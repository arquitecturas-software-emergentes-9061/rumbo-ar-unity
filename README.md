# Rumbo AR prototype (Android)

Unity 6000.3.26f1, URP, AR Foundation/ARCore 6.7.1, XR Plug-in Management 4.7.0. Open `Assets/Scenes/RumboArPrototype.unity`. Without a route the original manual arrow demo is preserved. Navigation uses only a route supplied by Flutter and a valid map–AR calibration; the demo heading is never used for navigation. There is no built-in route, native BLE scanner, backend client or A* implementation.

## Export into Flutter

Install **Android Build Support** for Unity 6000.3.26f1 (including SDK/NDK/OpenJDK) in Unity Hub. In Unity choose **Rumbo → Export Android library**. This switches the build target to Android and generates `Builds/Android/unityLibrary` beside the Flutter repository. Mobile's Gradle settings include that module only when it exists. Confirm that directory exists before building `rumbo-mobile-application` with `flutter build apk --debug`; an APK built without it contains Flutter and BLE but not Unity. Run the integrated APK on an ARCore-capable Android phone (API 25+, ARM64).

The demo is reached through Flutter **Tu ruta → Abrir prueba AR** in debug builds. Choose a heading in Flutter. Unity requests camera permission, shows tracked horizontal surfaces, places an anchored arrow when a tracked plane is tapped, turns it with the left/right buttons, and returns to Flutter with **Exit to Flutter**. If the library is absent, Flutter displays a controlled error. The Unity activity reports status and UTC timestamps through `com.uitopic.rumbo/ar/events` and appends them to `rumbo_ar_tracking.csv` under Unity's `Application.persistentDataPath`. After returning to Flutter, choose **Exportar registro AR** to save that file. The BLE channel remains separate.

## Navigation contract v1 (Mobile implementation pending)

Android calls `UnityPlayer.UnitySendMessage("RumboArController", method, json)` on its UI thread **after** the `navigation_ready` event. The named GameObject and public receivers exist in the original scene and in scenes regenerated by `RumboArSceneBuilder`: all behavior lives in its existing controller; no extra scene component is required. This repo does not implement a Flutter channel that forwards these messages. Existing Java `reportStatus`, `reportLogPath`, demo intent and activity `finish()` calls are unchanged; no new native methods are assumed.

Every JSON message has `protocolVersion: 1`, nonempty `sessionId`, `siteId`, `floorId`, `mapVersion`. IDs are case-sensitive, maximum 128 characters. Payload limit: 512 KiB. Coordinates and numeric scalars are finite **arrays**, so absent fields cannot silently become a valid zero. The map is right-handed on its floor: `position: [x, y, elevation]` in map units; Unity uses `[x, up, z]` in meters. Map +x maps to Unity +x and map +y to Unity +z at zero yaw. No origin, scale, north or floor elevation is inferred.

| Method | Additional required fields |
| --- | --- |
| `ReceiveRoute` | `routeId`, positive monotonic `revision` per session (also across changed route IDs), `originNodeId`, `destinationNodeId`, `activeNodeId`, ordered `nodes` (2–2048). Each node: `nodeId`, `floorId`, `position: [x,y,elevation]`. Endpoints must match first/last node; target must be a node after the origin. IDs unique; consecutive horizontal positions distinct. |
| `ReceiveCalibration` | `arSpaceId`, unique `calibrationId`, `referenceId`, `mapOrigin: [x,y,elevation]`, `yawDegrees: [angle]`, `metersPerMapUnit: [scale]`, `confidence: [0..1]`. Uses the VIO sample captured by Unity, never a Unity position invented in Flutter. |
| `ReceiveProgress` | `routeId`, exact current `revision`, `activeNodeId`, `state` (`navigating`, `arrived`, `unknown`), `capturedAtUnixMs`, `confidence: [0..1]` (required for known progress). Progress is monotonic within a revision. `arrived` must target the destination. `unknown` suspends guidance and VIO advancement. |
| `ReceiveBleReference` | `arSpaceId`, current `calibrationId`, `position: [x,y,elevation]`, `capturedAtUnixMs`, `confidence: [0..1]`. Position is the estimated **device** position, not a beacon's fixed coordinates. Confidence must be calibrated by Mobile. |

Two string methods do not take JSON: `CaptureCalibrationReference(referenceId)` and `InvalidateCalibration(reason)`.

Calibration sequence: accept route → wait for normal AR tracking → call `CaptureCalibrationReference` → obtain `calibration_reference` from the existing status channel. Its `reason` contains JSON with `protocolVersion`, `sessionId`, `arSpaceId`, `referenceId`, `capturedAtUnixMs`, `unityPosition: [x,up,z]` and `cameraYawDegrees`. Mobile must pair that instant with a trustworthy physical map position **at camera/device height**, and an independently established map-to-AR yaw and scale, then call `ReceiveCalibration` within 30 seconds. The Unity position is informational; Unity retains the actual sample. A floor point must not be paired with the camera position without accounting for camera height. BLE alone cannot establish yaw. Until this calibration exists, the guide stays hidden.

Calibration yaw is clockwise from Unity +z toward +x for map +y; map +x rotates with the same transform. Scale applies to all three map coordinates. A live calibration is refined using BLE translation, not replaced abruptly. Use `InvalidateCalibration` for a new physical reference; route, destination and active node remain. An AR session reset or removed anchor invalidates calibration and issues a new `arSpaceId`; Mobile must discard references from the previous space. A different site, floor, map version or destination requires a **new `sessionId` and calibration**. Multi-floor routing must be split by Mobile into floor-specific sessions; Unity never flattens a stair/lift edge onto a floor.

Reroutes in the same context preserve anchor, correction, calibration and session. Mobile supplies the corresponding `activeNodeId` in the new graph with a higher revision; Unity does not reuse an old graph index or reset to the first node. Calibrated, tracked VIO may advance one waypoint when the camera is within 0.8 m horizontally. It never advances by time or manual heading. Explicit unknown location suspends this until trustworthy progress/BLE or a new calibration restores it.

BLE uses the device's UTC epoch milliseconds at **capture**, with the same clock as Unity (`DateTimeOffset.UtcNow`), not receipt time or beacon clock. Mobile must convert monotonic timestamps before sending. Unity retains five seconds of VIO, interpolates only between samples within 150 ms of capture, and never extrapolates across a tracking gap. Defaults in controller `navigationSettings`: confidence ≥0.75; BLE age ≤2 s, progress age ≤3 s; no future/duplicate/out-of-order samples; residual ≤2 m, total correction ≤5 m; exponential time constant 2 s, speed ≤0.25 m/s. Invalid observations leave the current correction unchanged. During stale/missing BLE or lost tracking correction freezes; a fresh matched observation resumes it. Large errors are reported for explicit physical recalibration, never clamped into an apparently valid location.

The correction is `VIO_at_capture - calibrated_map(BLE_device_position)`, horizontally in the stable AR anchor frame. It adjusts only the guide's transform, never the camera, XROrigin, ARCore pose or anchor transform. One arrow and one anchor are reused across segment changes, BLE updates and reroutes. Arrow position/rotation changes are bounded (3 m/s and 180°/s); the candidate position must hit a tracked upward horizontal plane within 0.25 m of calibrated floor height. No detection at that position means no arrow. Tracking loss hides it immediately; recovery reuses the anchor if still valid. BLE does not correct yaw or height drift.

Outbound navigation events reuse `Report(state, reason)`: `navigation_ready`, `route_accepted`, `calibration_reference`, `calibration_accepted`, `progress_accepted`, `segment_changed`, `arrived`, `ble_accepted`, `navigation_guide`, `calibration_required`, `navigation_error`. Normal events include session/route/revision/active node/calibration identifiers in `reason`; errors include `message` and `code`. `navigation_guide` reports visibility or the blocking condition on changes. `calibration_required` carries the current `arSpaceId`. Existing tracking states and CSV logging remain available. Invalid incoming messages are rejected atomically; the last valid route remains. Mobile must consume errors and decide whether to resend or show its own TS-16 fallback.

## Automated verification

`Assets/Tests/EditMode/NavigationTests.cs` uses Unity Test Framework 1.6.0, already present. All routes and BLE inputs in tests are synthetic. Run with `unity test . --mode EditMode --output Logs/Sprint2-editmode.xml --timeout 300 -- -nographics -logFile Logs/Sprint2-editmode.log`, or Unity Test Runner. Tests cover the map transform, contract validation and JSON reception, segment turns/reroutes, correction sign, bounds/smoothing, one-hour synthetic drift with a ten-minute BLE gap, stale/invalid references, tracking visibility/recovery, preserved session/progress, VIO interpolation and original scene references. These are software tests, not physical AR/BLE measurements.

`Assets/Tests/PlayMode/NavigationControllerTests.cs` exercises actual public receivers and arrow hiding/reuse with synthetic messages and a plain GameObject; no ARCore provider is simulated. Run `unity test . --mode PlayMode --output Logs/Sprint2-playmode.xml --timeout 300 -- -nographics -logFile Logs/Sprint2-playmode.log`. Verification on 2026-11-23 with Unity 6000.3.26f1: **61/61 EditMode and 3/3 PlayMode passed**, no skipped tests. The initial sandboxed attempt failed during licensing before a verdict; final runs outside that restriction passed. Android Build Support is not installed here, so Android/IL2CPP export and APK integration remain unverified. Implementation used the installed Unity skill references `unity-cli.md` and `build-run-test.md`; no packages or Editor versions were changed.

## Physical validation

On a real ARCore-capable phone, test: permissions granted/denied; no surface; floor/table detection; anchored arrow and direction buttons; normal, limited and lost tracking while changing light and moving or occluding the camera; disappearance and recovery of the arrow; exit and re-entry into Flutter; BLE capture continuity if active. Collect device model, Android/ARCore versions, timestamps and observed outcomes. No physical AR test has been run in this repository.

Sprint 2 also needs: a real graph route and reroute from Mobile, surveyed floor/map calibration, camera/device-height agreement, verified capture timestamps/confidence, long indoor walks with measured drift, beacon dropout/recovery, offsets above thresholds, anchor relocalization, correct floor changes, and an integrated ARM64 APK. The eight WIs remain **partial end-to-end** until these external integrations and physical acceptance checks pass; code or synthetic tests alone do not complete them.
